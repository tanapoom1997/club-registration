# Security

- **รหัสผ่านเริ่มต้น:** สุ่มรายคน (10 ตัว ไม่มีตัวที่อ่านสับสน) ห้ามใช้เลขบัตร/วันเกิด ไม่มีที่ไหนเก็บรหัสจริง: admin เลือกชั้น (ห้องเดียวหรือทั้งชั้น ครั้งละไม่เกิน 1 ชั้น) แล้วกดออกรหัส server สุ่มและ hash (argon2id) แล้วตอบเป็นไฟล์ .xlsx ทันที (1 ชีตต่อห้อง, `Cache-Control: no-store`, ชื่อไฟล์มีแค่ชั้น/ห้อง) ไฟล์นั้นคือสำเนาเดียว ทำหาย = ออกใหม่ ซึ่งทำให้รหัสเดิมใช้ไม่ได้ทันทีและ bump `session_version` ออกให้ได้เฉพาะนักเรียนที่ `must_change_password` ยังเป็นจริง นักเรียนที่ตั้งรหัสเองแล้วจะไม่ถูกเขียนทับ (นักเรียนที่ลืมรหัสใช้การรีเซ็ตรายคนในข้อถัดไป) บังคับเปลี่ยนตอน login แรก
  - hash ก่อนเปิด transaction (จำกัดทำพร้อมกัน 2 งานทั้ง server ให้ login ยังได้ thread) แล้วใน transaction สั้นๆ ถือ import lock (`pg_advisory_xact_lock(1, 1)`) ก่อน จากนั้น lock แถวที่ยังมีสิทธิ์ด้วย `SELECT … FOR NO KEY UPDATE` เขียนเฉพาะแถวนั้น ไฟล์มีเฉพาะคนที่ถูกเขียนจริง นักเรียนที่เปลี่ยนรหัสระหว่างนั้นถูกข้าม admin สองคนออกขอบเขตเดียวกันพร้อมกัน → นักเรียนแต่ละคนมีรหัสที่ใช้ได้รหัสเดียว คือรหัสในไฟล์ของ request ที่ commit ทีหลัง
  - **ไม่ชนกับการยืนยัน import:** ทั้งสองงาน lock แถว `users`/`student_profiles` หลายแถวโดยไม่เรียงลำดับเดียวกัน ถ้าถือพร้อมกันอาจ deadlock (40P01 = 500) การออกรหัสจึงถือ import lock ก่อนแตะแถวใด สองงานนี้จึงไม่เคยถือ row lock พร้อมกัน งานที่มาทีหลังรอจนอีกงาน commit (เฉพาะ transaction สั้นๆ ไม่รวมการ hash) ลำดับ lock ทั้งระบบและเหตุผลว่าไม่ deadlock กับการลงทะเบียนอยู่ใน `apps/api/src/services/round-lock.ts` เทสต์: `apps/api/test/initial-passwords-import-lock.test.ts`
  - `idempotencyKey` ถูกเก็บใน `password_issuances` คู่กับการออก ส่ง key เดิมซ้ำ = `409 idempotency_key_reused` (ไม่ออกซ้ำ เพราะการออกซ้ำทำให้ไฟล์ที่อาจพิมพ์ไปแล้วใช้ไม่ได้) หน้าเว็บสร้าง key ใหม่ทุกครั้งที่กดยืนยัน
  - log เฉพาะ admin id, ขอบเขต, จำนวน และเวลา ไม่ log ชื่อ รหัสนักเรียน หรือรหัสผ่าน rate limit 20 ครั้ง/10 นาที ต่อ admin
  - วัดจริงในเทสต์ (เครื่องพัฒนา 4 vCPU ไม่ใช่สเปค production, 4 รอบ): ออกรหัส 450 คนใช้ 6.6–7.1 วินาทีต่อ request เกือบทั้งหมดคือ hash ส่วน transaction + สร้างไฟล์ใช้ไม่ถึง 0.1 วินาที ต้องวัดซ้ำบนเครื่องจริง
- **รีเซ็ตรหัสผ่านรายคน (นักเรียนที่ลืมรหัส):** admin เท่านั้น ที่หน้า `/admin/initial-passwords` การ์ด "รีเซ็ตรหัสผ่านรายคน" กรอกรหัสนักเรียนแล้วยืนยัน (`POST /api/admin/students/password-reset` body `{ loginId, idempotencyKey }` strict) ได้ทั้งคนที่เปลี่ยนรหัสเองไปแล้วและคนที่ยังไม่เปลี่ยน ไม่มีทางรีเซ็ตเองจากหน้า login (หน้า login บอกให้ติดต่อครูที่ดูแลการลงทะเบียน) ใช้ได้เฉพาะบัญชี role student ที่มี `student_profiles` รหัสที่ไม่มีหรือเป็นบัญชี admin ตอบ `404 not_found` เหมือนกัน
  - server สุ่มรหัสใหม่ 10 ตัวแบบเดียวกับรหัสเริ่มต้น hash ก่อนเปิด transaction (ใช้ตัวจำกัด 2 งานตัวเดียวกับการออกรหัส) แล้วใน transaction สั้นๆ ถือ import lock ก่อน แล้ว lock แถว `users` ของนักเรียน (`FOR NO KEY UPDATE`, profile `FOR SHARE`) แล้วเขียน hash ใหม่, `must_change_password = true`, `password_issued_at = now()` และ bump `session_version` (session เดิมทุกเครื่องหลุดทันที) แบบไม่มีเงื่อนไข จึงไม่ชนกับการออกรหัสหรือ import (ทำทีละงาน) และนักเรียนต้องตั้งรหัสใหม่ตอน login ครั้งถัดไป
  - **แข่งกับนักเรียนเปลี่ยนรหัสเอง:** การเปลี่ยนรหัสของนักเรียนเขียนแบบ compare-and-set บน `session_version` ถ้ารีเซ็ต commit ก่อน การเปลี่ยนรหัสตอบ `401` ไม่เปลี่ยนอะไร ถ้าการเปลี่ยนรหัส commit ก่อน รีเซ็ตเขียนทับต่อ ทั้งสองแบบจบที่รหัสจากการรีเซ็ตและบังคับเปลี่ยนรหัส ไม่มีครึ่งๆ กลางๆ (เทสต์ `apps/api/test/admin-password-reset.test.ts`) การออกรหัสทั้งห้องที่ไม่ได้ติ๊ก "เฉพาะนักเรียนที่ยังไม่เคยได้รหัสผ่าน" หลังรีเซ็ตจะเขียนทับรหัสที่รีเซ็ตไว้ เหมือนรหัสที่ออกไปแล้วรหัสอื่น
  - คำตอบ `200 { student: { loginId, fullName, grade, classroom, seatNo }, password }` พร้อม `Cache-Control: no-store` คือสำเนาเดียวของรหัส หน้าเว็บแสดงครั้งเดียว ไม่ใส่ใน URL หรือ storage ของเบราว์เซอร์ และลบออกจากหน้า (และจาก cache ของ TanStack Query ด้วย `gcTime: 0`) เมื่อกด "เสร็จแล้ว" หรือออกจากหน้า ดูซ้ำไม่ได้ ถ้าหายต้องรีเซ็ตใหม่
  - ทุกครั้งที่สำเร็จบันทึกใน `password_resets` (admin_id, student_id, idempotency_key, เวลา ไม่เก็บรหัสหรือ hash) ใน transaction เดียวกัน key เดิมซ้ำ = `409 idempotency_key_reused` ไม่รีเซ็ตซ้ำ หน้าเว็บสร้าง key ใหม่ทุกครั้งที่กดยืนยัน และส่ง key เดิมเฉพาะปุ่ม "ลองอีกครั้ง" เมื่อไม่รู้ผล (ถ้าคำขอแรกสำเร็จไปแล้วจะได้ 409 และหน้าเว็บบอกให้รีเซ็ตใหม่) และ log ด้วย `logAdminChange` (`student.password_reset`, admin id และ student id เท่านั้น ไม่ log ชื่อ รหัสนักเรียน หรือรหัสผ่าน) หลัง commit rate limit 60 ครั้ง/10 นาที ต่อ admin แยกจากงบของการออกรหัส
- **ตรวจสิทธิ์ที่ server ทุก endpoint** ไม่เชื่อ role/`student_id` จาก client ใช้ค่าจาก JWT เท่านั้น
- **Rate limit** ที่ `/auth/login` และ endpoint เขียน (ลง/เปลี่ยน/ยกเลิกและเข้า/ออก waitlist ของนักเรียนรวมกัน 30 ครั้ง/นาที ต่อนักเรียน, admin เพิ่ม/ย้าย/ลบนักเรียนแทนและลบรายชื่อรอแทนรวมกัน 120 ครั้ง/นาที ต่อ admin, คิวของนักเรียน: heartbeat + อ่าน 60 ครั้ง/นาที และ join + done 20 ครั้ง/นาที แยกจากงบการเขียน)
- **Session:** JWT (HS256, อายุ 2 ชม.) อยู่ใน cookie `HttpOnly; Secure; SameSite=Strict; Path=/api` ไม่เก็บใน `localStorage` ทุก request เช็ค `users.session_version` กับค่าใน token → logout หรือเปลี่ยนรหัส = token เก่าทุกเครื่องใช้ไม่ได้ทันที (สำคัญกับคอมห้องแล็บที่ใช้ร่วมกัน) และถ้า role ใน DB เปลี่ยน token เดิมก็ใช้ไม่ได้
- **บังคับเปลี่ยนรหัสครั้งแรก:** ถ้า `must_change_password` ทุก route ตอบ `403 password_change_required` ยกเว้น `/auth/me`, `/auth/change-password`, `/auth/logout`
- **คิวเลือกชุมนุม (README Phase 3 Q2):** ในรอบที่เปิดอยู่ `GET /api/student/clubs` ลง เปลี่ยน และเข้ารายชื่อรอของนักเรียนต้องมี ticket `admitted` ที่ยังไม่หมดอายุ ไม่งั้น `403 queue_required` ตรวจใน transaction ของการเขียนหลัง round lock, replay ของ key และการตรวจช่วงเวลา (ไม่ใช่ preHandler) ด้วยนักเรียนจาก session เท่านั้น ยกเลิก ออกจากรายชื่อรอ `GET /api/student/round` และ route ของ admin ไม่ต้องมี ticket `queue_required` ไม่ใช่การขาดสิทธิ์: หน้าเว็บไม่ logout และพากลับไปหน้ารอคิว รอบที่ admin ตั้งเป็นไม่มีคิว (`max_active` NULL, Q4) ไม่ต้องมี ticket gate อ่านค่านี้ใน statement เดียวกับ ticket หลัง round lock ซึ่งการแก้รอบก็ต้องถือ จึงไม่มีจังหวะที่การเขียนถูกตัดสินด้วยค่าที่เปลี่ยนกลางคำขอ นักเรียนเห็นแค่ `hasQueue` ไม่เห็นตัวเลขหรือจำนวนคนในคิว
- **CSRF:** `SameSite=Strict` + endpoint เขียนรับเฉพาะ JSON (form ข้ามเว็บส่ง `application/json` ไม่ได้ถ้าไม่ผ่าน CORS preflight ซึ่งเราไม่เปิด) ส่วน route อัปโหลด (multipart ซึ่ง form ข้ามเว็บส่งได้) ตรวจเพิ่มว่า `Sec-Fetch-Site` เป็น `same-origin`/`none` หรือถ้าไม่มี header นี้ `Origin` (ถ้าส่งมา) ต้องตรงกับ host (`apps/api/src/http/same-origin.ts`) ไม่ผ่าน = `403`
- **Rate limit login:** 10 ครั้ง/15 นาที ต่อ IP + รหัสผู้ใช้ (คนอื่นแกล้งล็อกบัญชีนักเรียนจากที่อื่นไม่ได้) และ 600 ครั้ง/นาที ต่อ IP ที่ตั้งสูงเพราะทั้งโรงเรียนอาจออก NAT IP เดียว **ต้องปรับตอน load test** store อยู่ใน memory ใช้ได้เพราะเป็นเครื่องเดียว และหลัง Caddy ต้องตั้ง `TRUST_PROXY=true` ไม่อย่างนั้นทุก request จะมี IP ของ Caddy และนับรวมเป็นก้อนเดียว
- **เวลาตอบของ login ไม่บอกว่ามีบัญชีไหม:** login ที่ไม่มีผู้ใช้ และบัญชีที่ยังไม่ได้ออกรหัส (`!unissued` นักเรียนที่ import แล้วแต่ admin ยังไม่ออกรหัสเริ่มต้น) หรือ hash ที่ใช้ไม่ได้ ยังคำนวณ argon2 ด้วยค่าเดียวกับการตรวจรหัสจริงหนึ่งรอบ (`spendVerifyWork` ใน `apps/api/src/auth/password.ts` ทุกทางที่ `verifyPassword` ตอบ "ไม่ตรง" โดยไม่ต้อง derive) เวลาตอบจึงไม่บอกว่ารหัสนักเรียนไหนมีอยู่จริงหรือยังรอรหัส เทสต์เทียบ median ของเวลาแบบสลับกันไปมา (`apps/api/test/support/timing.ts`) ต้องได้อย่างน้อยครึ่งหนึ่งของการใส่รหัสผิด ก่อนแก้ บัญชีที่ยังไม่ออกรหัสตอบเร็วกว่าราว 14 เท่า (ประมาณ 2 ms เทียบกับ 29 ms ผ่าน HTTP)
- **Admin คนแรก:** `pnpm --filter api create-admin <login_id>` สุ่มรหัส 16 ตัว แสดงครั้งเดียว เก็บแค่ hash และต้องเปลี่ยนตอน login แรก
- **Secret:** `JWT_SECRET`, DB password อยู่ใน env / SSM Parameter Store ห้ามอยู่ใน repo หรือ image บนเครื่องเก็บใน `deploy/production.env` (`chmod 600`, gitignored ด้วย `*.env`) ที่ทำจาก `deploy/production.env.example` ซึ่งไม่มีค่าจริง
- **ข้อมูลติดต่อครู** (เบอร์, อีเมล, LINE ID ทุกช่องเป็น optional): เห็นเฉพาะ admin (หน้า `/admin/clubs`) **นักเรียนเห็นแค่ชื่อครู** query ฝั่งนักเรียนไม่ SELECT คอลัมน์ติดต่อเลย (ใช้ `ADVISOR_NAMES_JOIN` ใน `services/clubs.ts` ตัวเดียวกับ export รายชุมนุม) และ response schema ของนักเรียนไม่มีช่องเหล่านี้ (serializer ตัดช่องที่ไม่อยู่ใน schema ทิ้งอีกชั้น) ถ้าวันหนึ่งจะให้นักเรียน ~2,500 คนเห็นช่องทางติดต่อ ต้องให้ครูยินยอมก่อน และใช้ช่องทางกลางของโรงเรียนถ้ามี
- **Event log และรายชื่อรอ** (`GET /api/admin/events`, `GET /api/admin/clubs/:id/waitlist`): มีชื่อและรหัสนักเรียน และชื่อ/รหัสของบัญชีที่ทำ จึงเป็น route ของ admin เท่านั้น (guard ก่อน validation) ไม่ส่ง `idempotency_key` และไม่ log คำตอบ (request line มีแค่ path และชื่อ parameter ไม่มีค่า) query ของ event log เป็น strict: parameter ที่ไม่รู้จัก = `400` แทนที่จะได้หน้าที่ไม่ได้กรอง
- **รหัสนักเรียนใน query string ของ event log** (PR 5b): `GET /api/admin/events?loginId=...` เป็น route เดียวที่รับข้อมูลส่วนตัว (รหัสนักเรียน) ใน query ค่านี้ไม่ถูกบันทึกที่ไหน: request log ของ api มีแค่**ชื่อ** parameter (`queryKeys: ["loginId"]` ไม่มีค่า เทสต์ใน `admin-events.test.ts` ส่งรหัสตัวใหญ่และรหัสผิดรูปแบบแล้วตรวจว่าไม่มีใน log) และ Caddy ไม่มี access log (`Caddyfile`) ห้ามเปิด access log ของ Caddy หรือ log query string เต็มใน api โดยไม่คิดเรื่องนี้ หน้าเว็บเก็บตัวกรองใน state ของ component เท่านั้น ไม่ใส่ใน URL ของหน้า รหัสจึงไม่อยู่ในประวัติของเบราว์เซอร์ (URL ของ `fetch` ไม่เข้าประวัติ) และ query ของ event log ใช้ `gcTime: 0` จึงไม่ค้างใน cache หลังออกจากหน้า
- **Frontend:** ห้าม `dangerouslySetInnerHTML` กับ `description` ที่ admin กรอก
- **Log:** ไม่ใส่ secret/PII พอสำหรับ debug serializer ของ logger อยู่ที่ `apps/api/src/log.ts` ที่เดียว (ใช้กับ logger ทุกตัวของ app รวมตัวที่เทสต์ใช้): request log มีแค่ method, path (ไม่มี query string), host และ**ชื่อ** query parameter (`queryKeys` ไม่มีค่า ชื่อที่ไม่ใช่รูปแบบตัวแปร เช่น ตัวเลขหรือภาษาไทย นับเป็น `queryKeysOmitted` เท่านั้น) เพราะ event log รับรหัสนักเรียนใน query (ดูข้อบน) และบรรทัดนี้เขียนก่อน validate client ที่ส่งผิดจึงใส่รหัสผ่านหรือรหัสนักเรียนใน query ของ route ไหนก็ได้ **ไม่มี IP** (IP คู่กับ request id และ student id ชี้ตัวเครื่อง/บ้านนักเรียนได้ Caddy ก็ไม่เก็บ access log ด้วยเหตุผลเดียวกัน) error log เก็บ field แบบ allowlist error จาก Postgres เก็บแค่ `code`, `constraint`, `table`, `column` ฯลฯ ไม่เก็บ `detail`/`where` (มีค่าของแถว) และ data exception (class 22) ไม่เก็บ message เพราะ Postgres ใส่ค่าที่ส่งมาไว้ใน message (เทสต์ `apps/api/test/logging.test.ts`)
- **Audit ของ admin:** สร้าง/แก้/ลบรอบ และแก้ชุมนุม ไม่มีตาราง audit ของตัวเอง (ไม่รับ `idempotency_key` เพราะส่งซ้ำได้ผลเดิม) จึงเขียน log หนึ่งบรรทัดหลัง commit ผ่าน `logAdminChange` (`apps/api/src/http/audit-log.ts`) มี `audit` (`round.create`, `round.create_batch`, `round.update`, `round.delete`, `club.update`), `adminId`, id ที่แก้, ชื่อ field ที่ส่งมา (`changed`) และค่าที่ไม่ใช่ข้อความหลังแก้ (เวลาเปิด/ปิด, `maxActive`, `capacity`) การแก้ชุมนุมที่ส่ง `capacity` มี `promoted` (จำนวนคนที่ได้ที่นั่งจากคิว) และ `promotedStudentIds` เมื่อมีคนได้ (ตัว promote เองอยู่ใน `registration_events` เป็น `waitlist_promote` ที่ `actor_id` = admin) ไม่ log ชื่อหรือคำอธิบายชุมนุม (admin พิมพ์เองอาจมีชื่อคน) admin เพิ่ม/ย้าย/ลบนักเรียนแทน (`club.member_assign`, `club.member_remove`) และลบรายชื่อรอแทน (`club.waitlist_remove`) มีบันทึกใน `registration_events` อยู่แล้ว (`admin_assign`/`admin_remove`/`waitlist_leave` actor = admin) แต่เขียนบรรทัดนี้ด้วยเพื่อให้ค้นการแก้ของ admin ได้ที่เดียว: `clubId`, `roundId`, `studentId` (id ของ DB), `outcome`, `fromClubId` เมื่อย้าย และ `promoted`/`promotedStudentIds` (การลบรายชื่อรอไม่ promote จึงไม่มีสองตัวนี้) ไม่มีชื่อนักเรียน รหัสนักเรียน (`loginId` ที่ admin ส่งมา) หรือชื่อชุมนุม คำขอที่ถูกปฏิเสธไม่มีบรรทัดนี้ ค้นด้วย `dcp logs api | grep '"audit"'` **ข้อจำกัด:** อยู่ได้นานเท่าที่ log rotation ของ container เก็บ (5 × 10 MB ใน `compose.prod.yml`) พอสำหรับตรวจย้อนวันลงทะเบียน ไม่ใช่บันทึกระยะยาว ถ้าต้องการต้องเพิ่มตาราง audit
- **Database role ของ api (least privilege):** api ต่อ DB ด้วย role `club_app` ไม่ใช่เจ้าของ DB (`POSTGRES_USER` ซึ่งเป็น superuser) migration `20261119000000_app-role.sql` สร้าง role แบบ `NOLOGIN` และ grant เฉพาะคำสั่งที่ api ใช้จริงรายตาราง: `registration_events`, `password_issuances` และ `password_resets` (migration `20261125000000_password-resets.sql`) ได้แค่ `SELECT`/`INSERT` (append-only ด้วยสิทธิ์อีกชั้นนอกจาก trigger), `club_advisors` ไม่มี `UPDATE`, `registrations` มี `UPDATE` เฉพาะคอลัมน์ `club_id` และ `created_at` (เปลี่ยนชุมนุม migration `20261120000000_change-registration-grants.sql`) ย้ายที่นั่งไปให้นักเรียนอื่นหรือรอบอื่นไม่ได้, `waitlist_entries` มีแค่ `SELECT`/`INSERT`/`DELETE` ไม่มี `UPDATE` (migration `20261121000000_waitlist-grants.sql`: ย้ายไปรอชุมนุมอื่น = ลบแล้วเพิ่มใหม่ จึงไปต่อท้ายคิวเสมอ และ api แก้ลำดับคิว `created_at` ชุมนุม นักเรียน หรือรอบของ entry ที่มีอยู่ไม่ได้), `queue_tickets` มี `SELECT`/`INSERT` และ `UPDATE` เฉพาะ `status`, `last_seen_at`, `admitted_at` ไม่มี `DELETE` (migration `20261123000000_queue-tickets.sql`: api เลื่อนลำดับคิว `created_at` หรือย้าย ticket ไปให้นักเรียน/รอบอื่นไม่ได้ และ trigger กัน ticket ที่จบแล้วกลับมาใช้ใหม่), `users` ลบไม่ได้, ไม่มีสิทธิ์ `TRUNCATE`, สร้าง/แก้ตาราง, อ่าน `pgmigrations` หรือใช้ `COPY … TO PROGRAM`/อ่านไฟล์บนเครื่อง DB ถ้า api มีช่องโหว่ (เช่น SQL injection) ความเสียหายจึงจำกัดอยู่แค่สิ่งที่ api ทำได้อยู่แล้ว
  - `migrate` ต่อด้วยเจ้าของ (`DATABASE_URL`) รัน migration แล้วตั้ง login ให้ `club_app` จาก `APP_DB_PASSWORD` ทุกครั้งที่ `up` (`apps/api/src/migrate.ts`) โดยส่งแค่ SCRAM verifier ที่คำนวณใน Node ไม่ส่งรหัสจริงไปกับ `ALTER ROLE` log ของ Postgres จึงไม่มีรหัส เปลี่ยนรหัส = แก้ `APP_DB_PASSWORD` ใน env file แล้ว `up` ใหม่
  - api ใน production (`NODE_ENV=production`) **ไม่ยอม start** ถ้า `DATABASE_URL` เป็น superuser, เจ้าของตาราง หรือสร้างของใน schema `public` ได้ (log `refusing to start` exit 1) ส่วนตอน DB ยังต่อไม่ได้ (หลัง reboot) จะรอและลองใหม่ทุก 2 วินาทีโดยยังไม่เปิดพอร์ต
  - role อยู่ระดับ cluster ไม่ใช่ระดับ DB ชื่อจึงตายตัว (`club_app`) dump มี `GRANT` ของ role นี้ไปด้วย restore ลง DB ใหม่บน server เดิมจึงได้สิทธิ์ครบ ส่วน server ที่สร้างใหม่ (volume ว่าง ยังไม่มี role) `scripts/restore.sh` สร้าง `club_app` แบบ `NOLOGIN` ก่อน `pg_restore` แล้ว migrate หลังสลับ DB ตั้ง login ให้ (smoke-backup ตรวจทั้งสองกรณี)
  - **ตารางใหม่ต้อง grant ใน migration เดียวกับที่สร้าง** และแก้รายการใน `apps/api/test/db-role.test.ts` ซึ่งเทียบสิทธิ์ทั้งหมดของ `club_app` กับรายการที่คาดไว้แบบตรงทุกตาราง และสิทธิ์รายคอลัมน์ที่เกินสิทธิ์ระดับตารางแบบตรงทุกคอลัมน์ (ตารางใหม่ที่ลืม grant หรือ grant เกินจึงล้ม) เทสต์ทั้งชุดรัน api และ fixture ด้วย `club_app` (ยกเว้น `TRUNCATE` ระหว่างเทสต์และ `seed-dev` ซึ่งเป็นเครื่องมือ dev) คำสั่งที่ไม่ได้ grant จึงล้มในเทสต์ก่อนถึง production
  - **dev ยังใช้เจ้าของ:** `pnpm dev` ใช้ `DATABASE_URL` เดียวใน `.env` ทั้ง migrate และ api (ไม่ตั้ง `APP_DB_PASSWORD` ก็ได้) การตรวจสิทธิ์จึงอยู่ที่เทสต์และ smoke ไม่ใช่ตอน dev
- **Backup:** dump มีข้อมูลส่วนบุคคลทั้งหมดและ hash รหัสผ่าน เก็บใน bucket private (Block Public Access) เข้ารหัส SSE-S3 role ของเครื่องเขียน/อ่านได้เฉพาะ prefix ของ backup ลบไม่ได้ ไฟล์ในเครื่อง 600 และไม่พิมพ์เนื้อหาออก log (ดู [Backup และ Restore (O3)](operations.md#backup-และ-restore-o3))
- **Repo เป็น Public:** ห้ามมีข้อมูลจริงทุกชนิด (นักเรียน ครู domain จริง IP ชื่อ bucket) เปิด secret scanning และ push protection แล้ว `.gitignore` กัน `*.xlsx` จริง / `samples/` / `.env*` / `*.dump` / `*.dump.partial` / `caddy-data-*.tar.gz` (เว้น `templates/`) และ CI ตรวจซ้ำด้วย `scripts/check-no-data-files.sh` (กัน `git add -f` ดู [Excel Import/Export](excel.md#excel-importexport)) ไฟล์จริงเก็บนอก repo ถ้าเผลอ push secret ต้อง rotate ทันที ลบจาก history ไม่พอ
- **แจ้งช่องโหว่:** [`SECURITY.md`](../SECURITY.md) ให้แจ้งแบบส่วนตัวผ่าน GitHub private vulnerability reporting (ห้ามเปิด issue สาธารณะ) และทดสอบได้เฉพาะสำเนาในเครื่องด้วยข้อมูลสมมติ ต้องเปิด **Settings → Code security → Private vulnerability reporting** ของ repo ก่อน ไม่อย่างนั้นปุ่ม Report a vulnerability ไม่ขึ้น
